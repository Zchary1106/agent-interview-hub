# Java 数据库与缓存：MySQL、事务、索引与 Redis

> 对应学习计划「数据库与缓存」阶段。目标：索引原理、事务隔离、缓存一致性与高可用都能讲清。

---

## 一、核心知识要点

### 1. MySQL 索引

- 默认 InnoDB 引擎，索引数据结构为 B+ 树：叶子节点存数据且有序，非叶子节点只存索引，天然适合范围查询。
- 聚簇索引（主键）与二级索引（回表）；覆盖索引可避免回表。
- 索引失效场景：对索引列使用函数/隐式类型转换、like '%xx'、联合索引不满足最左前缀。
- 设计原则：区分度高、查询频繁的列建索引；避免冗余索引；短索引优先。

### 2. 事务与隔离级别

- ACID：原子性（undo log）、一致性、隔离性（锁 + MVCC）、持久性（redo log）。
- 隔离级别：读未提交 → 读已提交 → 可重复读（MySQL 默认）→ 串行化。
- 幻读：可重复读下通过 MVCC（快照读）+ next-key lock（当前读）解决。
- MVCC：每行记录隐藏字段（事务 id、回滚指针）+ undo log 版本链 + ReadView。

### 3. Redis

- 数据结构：String、Hash、List、Set、ZSet（跳表）；每种结构的典型场景要能举例。
- 持久化：RDB（快照）与 AOF（追加日志）；AOF 有 always/everysec/no 三种策略。
- 过期与淘汰：惰性删除 + 定期删除；内存淘汰策略（LRU/LFU/随机等）。
- 高可用：主从复制 + 哨兵（故障转移），集群模式（slot 分片）。

### 4. 缓存与数据库一致性

- 常见问题：缓存穿透（查不存在的数据）、缓存击穿（热点 key 过期）、缓存雪崩（大量 key 同时过期）。
- 方案：穿透用布隆过滤器/空值缓存；击穿用互斥锁/逻辑过期；雪崩用随机过期时间 + 多级缓存。
- 一致性：先更新数据库，再删缓存（配合延迟双删或 binlog 订阅）；避免先删缓存再更新库。

## 二、常见误区

- 误区：事务里执行时间长没关系。纠正：长事务持锁久、undo log 膨胀，导致锁等待与回滚慢。
- 误区：缓存一定能提升性能。纠正：读多写少、热点集中的数据才适合缓存；写多场景缓存反而增加不一致风险。
- 误区：索引越多越好。纠正：索引占用空间并拖慢写入，需要按查询模式取舍。

## 三、高频面试题（附参考答案）

1. 为什么 MySQL 用 B+ 树而不是 B 树或哈希索引？

> B+ 树非叶子节点不存数据，单节点可容纳更多索引项、树更矮；叶子节点链表有序，范围查询与排序友好；哈希只适合等值查询，无法范围与排序。

2. 什么情况下索引会失效？

> 对索引列使用函数或运算、隐式类型转换（如字符串列与数字比较）、like 以 % 开头、联合索引不满足最左前缀、优化器认为全表扫描更快。

3. 事务隔离级别与幻读？

> 隔离级别从低到高：读未提交、读已提交、可重复读、串行化。MySQL 默认可重复读，通过 MVCC 快照读避免普通幻读；当前读（for update）通过 next-key lock 阻止幻读插入。

4. Redis 缓存与数据库如何保证一致性？

> 常用"先更新 DB 再删缓存"，删除失败用延迟双删或订阅 binlog 异步删除兜底；强一致场景直接读 DB 或引入版本号。没有银弹，重点是接受最终一致性并缩短不一致窗口。

5. 缓存穿透、击穿、雪崩的区别与处理？

> 穿透：查询不存在的数据 → 布隆过滤器/缓存空值；击穿：热点 key 过期瞬间高并发打到 DB → 互斥锁重建/逻辑过期；雪崩：大量 key 同时过期或 Redis 宕机 → 过期时间加随机值、多级缓存、限流降级。

6. 一条 SQL 的执行过程？

> 连接器（鉴权）→ 分析器（词法/语法）→ 优化器（选索引与执行计划）→ 执行器（按计划访问存储引擎）；InnoDB 通过 buffer pool 缓存页，redo log 保证崩溃恢复。
