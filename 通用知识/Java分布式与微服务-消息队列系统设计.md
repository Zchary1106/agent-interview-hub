# Java 分布式与微服务：消息队列与系统设计

> 对应学习计划「分布式与系统设计」阶段。目标：微服务拆分、分布式事务、消息队列可靠性、限流熔断与系统设计演练。

---

## 一、核心知识要点

### 1. 微服务基础

- 拆分原则：按业务域（DDD 限界上下文）拆分，独立部署、独立伸缩、独立故障域。
- 服务治理：注册中心（Nacos/Eureka/Consul）、配置中心、网关（路由/鉴权/限流）。
- 调用链：Feign/HTTP 或 gRPC；超时、重试与熔断必须显式设计，避免级联故障。

### 2. 分布式事务与一致性

- 2PC / TCC：强一致方案，事务管理器协调，注意协调者单点与悬挂事务。
- 最终一致性：本地消息表、事务消息（RocketMQ）、Saga 补偿。
- 幂等设计：接口幂等键（唯一索引/状态机/去重表），保证重复请求不产生重复副作用。

### 3. 消息队列

- 选型：Kafka（吞吐高、日志流）、RocketMQ（事务消息、延迟消息）、RabbitMQ（灵活路由）。
- 不丢失：生产者 ack、broker 多副本（ISR）、消费者手动提交 offset。
- 不重复消费：消费端幂等（唯一业务键 + 状态校验）。
- 顺序消息：单分区单消费者 + 按业务键路由；堆积处理：扩容消费者/临时队列分流。

### 4. 限流、熔断与降级

- 限流算法：固定窗口、滑动窗口、漏桶、令牌桶；单机（Guava RateLimiter）与分布式（Redis + Lua）。
- 熔断：Sentinel/Hystrix，统计错误率或慢调用比例，进入 open/half-open 状态。
- 降级：超时降级、缓存降级、兜底返回（默认值/空数据）。

### 5. 系统设计通用框架

- 步骤：需求澄清（量级 QPS、数据规模、一致性/可用性取舍）→ 容量估算 → 架构图（接入层/服务层/数据层）→ 核心链路 → 故障与扩展性。
- 通用组件：负载均衡、缓存、异步削峰、分库分表、读写分离、监控告警。

## 二、常见误区

- 误区：系统设计必须"高大上"。纠正：先满足量级与一致性需求，组件越少越稳。
- 误区：分布式事务一定需要强一致。纠正：大部分业务可接受最终一致，强一致成本高。
- 误区：MQ 只用来解耦。纠正：MQ 引入顺序、重复、堆积问题，用前先评估是否真的需要。

## 三、高频面试题（附参考答案）

1. 如何保证消息不丢失、不重复？

> 不丢失：生产者同步确认、broker 副本同步（ISR）、消费者处理成功再提交 offset。不重复：消费端按业务唯一键幂等（唯一索引/状态机），配合手动提交 + 失败重试。

2. 分布式事务有哪些方案？

> 强一致：2PC/TCC（适合短事务、对一致性敏感）；最终一致：本地消息表、事务消息、Saga 补偿。选型看业务容忍的不一致时间与回滚复杂度。

3. 如何设计一个秒杀系统？

> 流量：网关 + 限流 + CDN 静态页；库存：Redis 预扣 + Lua 原子扣减，扣减成功才发 MQ 异步落库；防超卖：数据库唯一约束/乐观锁兜底；风控：同用户限购、验证码。

4. 熔断和限流有什么区别？

> 限流是保护自己（控制入口流量），熔断是保护下游（下游故障时快速失败）；两者常配合：限流在前置网关，熔断在调用链路上。

5. 微服务之间如何保证调用幂等？

> 调用方生成全局唯一 requestId，服务端用幂等表（requestId 唯一索引）去重；写操作配合状态机校验（如订单状态流转），重复请求返回上次结果。

6. Kafka 为什么吞吐高？

> 顺序写磁盘（追加日志）、页缓存、零拷贝（sendfile）、批量发送与压缩、分区并行消费。这也解释了为什么 Kafka 适合日志流而不适合强事务消息。

## 四、动手练习与掌握标准

- 练习：用一个 3 服务 demo 串联"下单 → 扣库存 → 发 MQ → 异步通知"，验证幂等与重试；用 Sentinel 配置一个限流 + 熔断规则。
- 掌握标准：能画出秒杀/订单系统的架构图；能解释"为什么用 Redis 扣库存而不是数据库行锁"；能设计一套最终一致性方案并指出不一致窗口。
