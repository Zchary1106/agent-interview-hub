# Java 项目表达：架构、指标、故障与技术取舍

> 对应学习计划「Java 项目表达」阶段。目标：把项目经历讲成"背景 → 方案 → 指标 → 取舍"，让面试官快速判断你的工程深度。

---

## 一、项目表达框架（STAR + 技术化）

| 环节 | 要讲清楚 | 反例 |
|------|---------|------|
| 背景（S） | 业务问题与规模：QPS、数据量、团队规模 | "我做了个管理系统" |
| 任务（T） | 你负责的边界与目标（性能/稳定性/成本） | "参与了开发" |
| 方案（A） | 架构决策、选型对比、为什么这样取舍 | 只罗列技术栈 |
| 结果（R） | 可量化指标：延迟、吞吐、错误率、成本 | "性能提升了" |

## 二、技术取舍怎么讲

- 每次选型给出 2–3 个候选 + 对比维度（一致性/吞吐/复杂度/运维成本）+ 最终选择。
- 例：缓存选型 Redis vs 本地缓存 → 一致性要求高选 Redis；读多写少热点场景本地 + Redis 两级缓存。
- 例：消息队列 Kafka vs RabbitMQ → 高吞吐日志流选 Kafka；复杂路由与优先级选 RabbitMQ。
- 承认取舍的代价：选择了最终一致性就要接受不一致窗口，并给出补偿方案。

## 三、常见故障与复盘模板

| 故障类型 | 常见根因 | 排查思路 |
|---------|---------|---------|
| 接口变慢 | 慢 SQL、锁等待、GC 停顿 | 链路追踪 → 慢查询 → explain → 压测复现 |
| 内存溢出 | 大对象、连接/线程泄漏、缓存无上限 | heap dump 分析、jmap 直方图、OOM 日志 |
| 服务雪崩 | 超时重试放大、线程池打满 | 熔断降级、信号量隔离、快速失败 |
| 数据不一致 | 双写未做幂等、缓存未删 | 核对日志时序、补偿任务、binlog 订阅 |

复盘话术：现象 → 影响面 → 定位过程（证据链）→ 根因 → 修复 → 预防（监控/告警/演练）。

## 四、常见误区

- 误区：只讲功能不讲数字。纠正：每个项目至少准备 3 个指标（延迟、吞吐、可用性/错误率）。
- 误区：把团队成果说成个人成果。纠正：明确区分"我负责的"与"协作的"，重点讲个人决策。
- 误区：故障讲得模糊。纠正：故障复盘是加分项，讲清定位方法与预防措施比结果更重要。

## 五、高频面试题（附参考答案）

1. 挑一个项目，讲清你的技术方案与取舍。

> 按 STAR 讲：背景给量级（如订单接口 2k QPS、P99 500ms）；方案讲清架构与关键决策（如引入 Redis 缓存 + MQ 异步化，对比了本地缓存与直连 DB）；结果给指标（P99 降到 80ms，错误率 0.2% → 0.05%）；最后讲取舍代价（最终一致性，接受 1s 内不一致并做补偿）。

2. 你遇到过最大的线上故障是什么？

> 讲"现象 → 影响面 → 定位 → 根因 → 修复 → 预防"：例如缓存 key 集中过期导致 DB 打满，通过日志定位热点 key、随机过期 + 互斥锁重建修复，并加 DB 连接池告警与 Redis 命中率看板预防。

3. 你的系统如何保证可用性？

> 分层回答：架构层（无状态多副本、读写分离、故障域隔离）、依赖层（超时重试熔断降级）、数据层（主从/多活、备份恢复演练）、观测层（指标告警、链路追踪、容量压测）。

4. 如何评估一次重构或技术升级的效果？

> 先定基线（重构前指标）→ 灰度发布（按流量/租户）→ 对比指标（延迟、错误率、资源、成本）→ 结论与回滚预案。用数据说话，不凭感觉。

## 六、动手练习与掌握标准

- 练习：把自己最熟的项目按 STAR 模板写一页纸，标出 3 个指标与 2 个技术取舍；准备 1 个故障复盘故事。
- 掌握标准：任何项目问题都能在 3 分钟内讲完"背景 → 方案 → 指标 → 取舍"；面试官追问细节时能用证据链回答。
